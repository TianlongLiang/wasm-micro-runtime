# Q&A: `K_THREAD_DEFINE` vs. dynamic thread allocation in a Zephyr user-mode library

This document records three related questions asked during the design review
of `dev/user_mode_multithread_fix` and their empirically-verified answers.
Both regression tests referenced here (probe 1 and probe 2) live in
`product-mini/platforms/zephyr/user-mode/lib-wamr-zephyr/wamr_lib.c` and
run in the ST variant of the user-mode sample.

For the broader mechanism (kobject registration gap, `WAMR_BUILD_ZEPHYR_USERMODE_MT`
flag, etc.), see [`zephyr-usermode-internals.md`](zephyr-usermode-internals.md).

---

## Q1. Why can't we `K_THREAD_DEFINE` inside a user-mode library — why do we have to use dynamic threads?

Two reasons stack up. One is a design choice; the other is a technical wall.

### The design reason (primary)

`os_thread_create` is a **runtime** API. Callers ask for a new thread at
runtime, with a runtime-chosen entry function and argument. WASM modules
load at runtime; thread counts come from configuration. `K_THREAD_DEFINE`
is a compile-time macro — using it means declaring a fixed pool of thread
slots with fixed entry functions and building a slot-allocation layer on
top. That is strictly more code than calling `k_object_alloc(K_OBJ_THREAD)`
on demand, for no functional benefit. WAMR chose the simpler path.

### The technical reason (verified empirically in this branch)

Even if you accepted the static-pool complexity, `K_THREAD_DEFINE` inside
a `zephyr_library_app_memory(wamr_partition)`-tagged TU does not actually
work. The k_thread control block lands in the TU's `.data` section, which
the linker fragment generated by `zephyr_library_app_memory` remaps into
the `app_smem` section (the user-writable partition region).

Zephyr's build-time scanner (`scripts/build/gen_kobject_list.py`, lines
669–675) then applies an **intentional security check**:

```python
if not user_ram_allowed and (
    (app_smem_start <= addr < app_smem_end)
    or (app_smem_pinned_start <= addr < app_smem_pinned_end)
):
    debug(f"object '{ko.type_obj.name}' found in invalid location {hex(addr)}")
    continue   # drop from gperf table
```

Where `user_ram_allowed=False` for `k_thread` (line 102 of the same file).
The **reason for the check** is that a k_thread struct writable from user
mode would let user code corrupt scheduler state and escalate privileges.
This is a policy dating to when Zephyr introduced userspace — not a
scanner bug, and not something a Zephyr version bump will fix.

Running the scanner in verbose mode on our build produces the exact
diagnostic line:

```
gen_kobject_list.py: object 'k_thread' found in invalid location 0x13cb40
```

The k_thread never makes it into the gperf table. Any user-mode syscall
that references it (`k_wakeup`, `k_thread_abort`, etc.) fails with:

```
<err> os: 0x13cb40 is not a valid k_thread
<err> os: address is not a known kernel object
```

### Why this differs from `K_SEM_DEFINE` (which does work)

`k_sem` carries the same `user_ram_allowed=False` policy flag. It avoids
the scanner filter not because the check is exempted for semaphores, but
because `K_SEM_DEFINE` places the object in a per-type iterable section
(`k_sem_area`) that is kernel-owned globally and is NOT remapped by
`zephyr_library_app_memory`. So the k_sem's address falls outside
`_app_smem_start.._app_smem_end` and the check passes. `K_THREAD_DEFINE`
uses no such kernel-owned iterable section — the k_thread struct is
placed directly in the TU's `.data`.

### WAMR's actual workaround

`k_object_alloc(K_OBJ_THREAD)`. It allocates from the **kernel heap**
(sized by `CONFIG_HEAP_MEM_POOL_SIZE`), which sits outside `app_smem`, and
registers the object in the kernel object table at runtime. This
satisfies both the security policy (kernel heap is not user-writable) and
the visibility requirement (runtime registration is a first-class code
path, not a gperf artifact). This is what `WAMR_BUILD_ZEPHYR_USERMODE_MT=1`
turns on inside `os_thread_create_with_prio`.

## Q2. If it's NOT a user-mode library — will `K_THREAD_DEFINE` work?

Yes.

Without the `zephyr_library_app_memory(wamr_partition)` call, the TU's
`.data` section stays in the kernel's default `.data` segment — outside
`_app_smem_start.._app_smem_end`. The scanner's `user_ram_allowed`
security check does not fire (its address range condition is false). The
k_thread ends up in the gperf table normally. `k_wakeup`, `k_thread_join`,
etc. from user mode work after the standard `k_object_access_grant(&t,
tid)` from supervisor mode.

This is the ordinary Zephyr pattern: any application code that uses
`K_THREAD_DEFINE` in `main.c` (which is not partitioned) already relies
on this working, and it does.

However: WAMR would still prefer dynamic threads for the design reason
in Q1 (runtime API vs. compile-time pool). The technical obstacle
disappears, but the API mismatch remains. So the answer for WAMR
specifically stays "use dynamic allocation" even in a non-partitioned TU.

## Q3. If we `K_THREAD_DEFINE` a KERNEL-mode thread in the user-mode library — will it error?

Yes, in a specific way that's worth understanding.

The `K_USER` flag on `k_thread_create` (and inside `K_THREAD_DEFINE`)
controls **what CPU mode the thread runs in**, not **where the k_thread
control block lives in memory**. The struct's placement is determined
solely by which section its symbol lands in — the TU's `.data`, which
`zephyr_library_app_memory` remaps to `app_smem`.

So a kernel-mode `K_THREAD_DEFINE` in `wamr_lib.c`:

- **The thread itself runs fine, if you can start it.** Kernel-mode
  threads bypass MPU checks — they can read and write any memory. Partition
  membership does not restrict them. If the thread ever gets scheduled it
  will execute correctly and can touch anything in the address space.

- **But any user-mode syscall on it faults.** The k_thread struct still
  ends up in `app_smem` and still gets dropped by the scanner's
  `user_ram_allowed=False` filter. So `k_wakeup(&t)` from a user-mode
  thread → syscall handler runs `z_vrfy_k_wakeup` → looks up the k_thread
  in the kernel object table → not found → faults with `not a valid
  k_thread`.

- **Supervisor-mode operations on it work, because kernel-mode callers
  bypass the syscall validation entirely.** So `k_wakeup(&t)` from
  `main()` (before it drops into user mode) is legal and would actually
  start the kernel-mode thread.

The empirical confirmation lives in probe 2 in `wamr_lib.c`. It defines a
kernel-mode `K_THREAD_DEFINE(wamr_partition_kthread_probe, ..., 0, K_TICKS_FOREVER)`
(never auto-starts). `src/main.c` (kernel mode) then reads
`wamr_partition_kthread_probe` (the tid) and prints it — this works
because the print is from supervisor. If we tried to `k_wakeup` on the
same tid from the user-mode entry thread, we would fault (originally
verified in an early revision of probe 2 that has since been trimmed to
the observational form). The tid value visible in the boot log is
`0x137b40`, which lies inside `_app_smem_start=0x137000`..`_app_smem_end=0x14d000`
— confirming the scanner's filter fired for exactly the reason described.

### Practical implication

You can technically have kernel-mode threads defined in `wamr_lib.c` if
you only ever interact with them from supervisor code (kernel `main()`
before user-mode entry, or from syscalls implemented on the kernel side).
But it's a strange design: why put a thread inside a library if the
library's own user-mode code can't touch it? For any pattern where
library code interacts with the thread, `k_object_alloc(K_OBJ_THREAD)`
is the correct workaround, and it also removes the compile-time-pool
limitation.

## Summary table

| Scenario | Static thread struct in gperf? | User-mode syscall on it |
|---|---|---|
| `K_THREAD_DEFINE(t, ..., K_USER, ...)` in `wamr_lib.c` (partitioned TU) | NO — filtered by scanner (address in `app_smem` + `user_ram_allowed=False`) | Faults: `not a valid k_thread` |
| `K_THREAD_DEFINE(t, ..., 0, ...)` (kernel-mode) in `wamr_lib.c` (partitioned TU) | NO — same filter, K_USER flag doesn't change placement | Faults: `not a valid k_thread` |
| `K_THREAD_DEFINE(t, ..., K_USER, ...)` in `main.c` (non-partitioned TU) | YES — address in kernel `.data`, filter doesn't apply | Works after `k_object_access_grant(&t, caller)` |
| `k_object_alloc(K_OBJ_THREAD)` at runtime (any TU) | YES — kernel heap outside `app_smem`, registered at alloc time | Works; child threads can inherit via `K_INHERIT_PERMS` |

WAMR uses row 4 exclusively for user-mode-visible threads.
